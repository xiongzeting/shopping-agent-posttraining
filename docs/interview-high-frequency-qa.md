# 第一部分：长程购物 Agent

## 一、项目介绍与整体设计

### Q1：请用 30 秒介绍一下购物 Agent 项目。

我做的是一个长程购物 Agent 的后训练闭环。模型要在淘宝商品快照环境里，通过搜索、比较候选、核验详情、选择规格和购买等工具完成最多 45 步的任务。

我先用 Teacher 轨迹做 LoRA SFT，让 Qwen3.5-2B 学会合法使用工具和完成基本流程；再用 veRL 和 vLLM 做在线 GRPO，优化搜索、比较、停止探索和最终决策；最后在与训练集零重叠的 Final-240 上，用环境 Reward、冻结 Rubric、盲轨迹 Judge 和效率指标做评测。最终正确购买率从 Base 的 0% 提升到纠错 SFT 的 68.33%，GRPO230 配合 Harness v3 达到 81.25%，超过同协议 Qwen3.8-27B v3 的 75.42%。

### Q2：这个项目最难的地方是什么？

最难的不是生成一段答案，而是保证几十轮交互里模型、Harness 和环境一直处在同一个状态上。

具体包括四类问题：模型会生成当前页面不存在的动作；长历史会挤爆上下文；终局 Reward 必须可验证，不能把基础设施错误当模型失败；在线 GRPO 还要保证同一任务的多条轨迹确实有可学习的组内差异。

### Q3：为什么购物任务适合做 Agentic RL？

因为它天然是一个部分可观测、长时序、有状态转移的决策问题。模型每一步只能看到当前页面和历史证据，前面的搜索词、候选选择和规格操作都会影响后续状态。

最终买对或买错又是可程序验证的，所以它同时具备长程决策和可计算终局奖励，比较适合做在线 RL。

### Q4：完整训练流程是什么？

我把流程固定成 Baseline → SFT → GRPO → Evaluation。

Baseline 用来确认 Base 模型在工具协议上的真实起点；SFT 先建立可执行策略；GRPO 在真实环境 Rollout 上优化策略；最后用冻结评测集统一比较。训练、模型合并和 Final-240 评测是三个独立阶段，不能边看 Final 结果边调训练数据。

### Q5：你在项目里的核心贡献是什么？

我主要做了四块：Teacher 数据质量门和纠错数据构造、Reward v4 与 GRPO 动态采样、Harness 与长上下文工程、Final-240 评测与归因分析。

如果面试官继续追问，我会优先展开 Reward 和 Harness，因为这两块最能体现环境型 Agent 与普通文本训练的区别。

### Q6：为什么不用一个更大的模型直接做？

更大模型确实有更强的先验能力，但不代表它天然适配这个环境的工具协议、页面状态和终局定义。

同协议下，2B 的 GRPO230 v3 正确购买率是 81.25%，27B v3 是 75.42%。这说明针对任务的数据、Reward 和 Harness 能弥补很大一部分参数规模差距。当然这不是证明 2B 普遍强于 27B，只能说明在当前环境和协议下，小模型后训练更有效。

## 二、Teacher 数据与 SFT

### Q7：为什么必须先做 SFT，不能从 Base 直接 GRPO？

因为 Base 几乎不会稳定完成工具协议。直接做 GRPO 时，同一个任务的四条轨迹很可能全是无工具回复、非法参数、循环或者根本到不了购买终局，组内 Reward 近似常数，没有有效 Advantage。

SFT 先解决“会不会做”，GRPO 再解决“怎么做得更好”。

### Q8：8,708 条 Teacher 候选是怎么来的？

这是五类候选池的汇总：普通稳定轨迹 4,762 条、Loop Recovery 1,886 条、Near-miss Rejection 1,746 条、Option Grounding 274 条、Terminal Tool Commit 40 条，总计 8,708 条。

最后不是随机抽 1,000 条，而是先过质量门，再按行为类型、轨迹长度和 Gold 检索位置做数据集级配平。

### Q9：为什么最后是 600 条普通数据加 400 条纠错数据？

600 条普通数据负责教稳定成功协议，400 条纠错数据针对模型已经暴露出来的具体失败模式。

400 条由 160 条循环恢复、101 条近似商品拒绝、99 条规格精确选择和 40 条终局工具提交组成。这样数据不只是展示“理想成功路径”，还展示遇到坏状态以后怎么恢复。

### Q10：三层质量门具体是什么？

第一层是结果门：必须完整 gold_purchase、reward_valid=true，目标商品和规格正确。

第二层是过程与关键动作门：Tool Call 可解析、Assistant 和 Tool 成对、动作基于最新 Observation、规格值真实存在、终局动作完整。

第三层是行为语义门：循环恢复必须真的发生过风险并恢复，近似商品拒绝要指出具体冲突，规格数据必须完成真实选择，分析结束后必须显式调用购买工具。

### Q11：为什么不能只按最终买对来筛 Teacher？

因为成功轨迹也可能包含大量偶然错误，比如先乱点几次、依赖 Guard 纠正、最后碰巧买对。模型会把这些过程一起模仿。

另一方面，过程门也不能过严。可恢复的错误如果全部整条删除，会把最有价值的恢复行为过滤掉，所以我区分“可恢复缺陷”和“污染状态的不可恢复缺陷”。

### Q12：如何保证 Teacher 数据有多样性？

我没有只看平均步数，而是同时约束轨迹长度、Gold 召回位置和动作模板分布。

最终短、中、长轨迹为 477、400、123 条；Gold Rank 1、2–5、6–20、21–150、缺失分别是 501、299、100、70、30；完整动作序列有 452 种，Top-1 只占 7.5%。这些指标比单纯说“轨迹长短都有”更可验证。

### Q13：为什么早期数据会集中在 8 步？

因为 Teacher Prompt 和筛选门共同产生了生存者偏差：固定模板更容易稳定成功，也更容易通过严格过程门，所以最后留下来的轨迹越来越像。

解决方法不是强行加无意义步骤，而是放宽可恢复过程门、按源任务难度采样，并检查动作序列和检索难度的联合分布。

### Q14：为什么不能把超长轨迹直接截断到 30K？

因为一条 Agent 轨迹不是普通文本。截断可能切掉 Tool Result、破坏 Assistant–Tool 配对、丢失规格证据或者直接删掉购买终局。

所以 SFT 数据采用整条删除再回填。最终 train 最大 29,533 tokens，validation 最大 29,994 tokens，全部完整落在 30K 内。

### Q15：什么是 Assistant-only Loss？

输入里仍然保留 System、User、Assistant Tool Call 和 Tool Observation，但只有 Assistant 生成的动作 Token 参与交叉熵损失，其他位置的 label 设为忽略。

这样模型重点学习可执行动作，不去拟合环境返回的长文本，也不蒸馏 Teacher 的私有推理，更不会把隐藏 Gold 信息当监督目标。

### Q16：为什么不用 Chain-of-Thought SFT？

这个任务真正需要监督的是外显动作和状态转移，不是 Teacher 的内部思维文字。

长 CoT 会增加上下文和训练成本，也可能把 Teacher 的表达习惯当成策略。我的做法是保留必要的公开证据，通过 Tool Call 和环境 Observation 让决策过程可追踪。

### Q17：SFT 的关键训练参数是什么？

Base 是 Qwen3.5-2B，BF16 LoRA，r=16、alpha=32、dropout=0.05，max length 30K，3 个 epoch，batch size 1，梯度累积 8，学习率 1e-4，warmup 3%。

使用 Flash Attention 2 和 Liger，QLoRA 关闭。最终 900 条训练、100 条验证，对应 339 个 optimizer step。

### Q18：为什么选择 LoRA 而不是全参数训练？

2B 模型虽然不算特别大，但 30K 长上下文和 Agent 轨迹会显著增加激活和优化器开销。LoRA 可以减少可训练参数和显存，同时保留 Base 能力，训练和导出也更灵活。

另外 GRPO 是在线训练，Rollout 与更新都比较贵，LoRA 更适合快速迭代和控制策略漂移。

### Q19：普通 SFT 和纠错 SFT 的提升说明了什么？

普通 1,000 条 Teacher 把正确购买从 0% 提升到 57.92%，说明 SFT 首先解决了协议冷启动。

把数据换成 600 普通＋400 纠错后达到 68.33%，额外提升 10.41 个百分点，说明针对真实 Bad Case 的数据比继续堆同质成功轨迹更有效。

### Q20：如何保证 SFT 与 Final-240 零重叠？

不仅查 task_id，还检查 ASIN、商品 family 和语义近重复。公开 metadata 中这四类 overlap 都是 0。

原因是只查 task_id 不够，同一商品或者改写后的同义任务仍可能泄漏。

## 三、Reward v4

### Q21：Reward v4 的核心思路是什么？

核心是把用户公开 Query 编译成可审计的约束合同，再根据终局商品逐条核验，而不是只比较一个隐藏 Gold ID。

它把要求分成 Hard、Soft、Ignore 和 Needs Review，区分 Gold、Valid、Partial、错误购买、循环、非法动作和停止，并保留每条约束的证据来源。

### Q22：Hard 和 Soft 怎么区分？

品类始终是 Hard。用户明确说“必须、不要、不超过、至少、只能”这类不可妥协且能确定性核验的要求，也进入 Hard。

“最好、优先、尽量、大约、左右、预算”等更像 Soft。复杂歧义表达不强行自动评分，而是进入 Needs Review 或审计项。

### Q23：为什么不能把所有属性都设成 Hard？

这样会让 Reward 过于脆弱。用户说“最好轻一点”和“必须支持某接口”的语义强度明显不同，如果都一票否决，模型会被迫过度保守。

Hard 负责安全底线，Soft 负责偏好排序，这样 Reward 才能表达“不能买”和“可以买但不是最优”的差别。

### Q24：Gold、Valid 和 Partial 有什么区别？

Gold 是命中目标商品并且所有可评分 Hard 通过，基础分 1.0。

Valid 是非 Gold 替代商品，但 Hard 全通过且没有可核验 Soft 失败，基础分 0.8。

Partial 是替代商品 Hard 全通过，但至少一个可核验 Soft 没满足，基础分是 0.5＋0.3×soft_score。Hard 失败永远不会进入 Partial，而是 Wrong Purchase。

### Q25：为什么严格成功只认 Gold，不把 Valid 算进去？

因为严格成功用来衡量是否完整命中冻结目标，必须有稳定、确定的标准。

Valid 对训练有价值，说明模型找到了满足用户要求的替代商品，但它与“命中目标商品”不是同一个指标，所以报告里同时给 Strict Gold 和 Gold＋Valid。

### Q26：Reward v4 各终局分数怎么设计？

Gold 1.0，Valid 0.8，Partial 为 0.5＋0.3×soft_score；Wrong Purchase -1.0，Assistant Final 和 Guard Rejection -0.8，Repeat Loop -0.6，Early Abstain -0.4，Max Steps 基础分 0。

reward_unverifiable 的数值是 0，但 reward_valid=false，它不是一个正常中性样本，而是必须从训练更新中隔离的无效样本。

### Q27：为什么错误购买比不购买惩罚更重？

错误购买已经产生了不可逆的用户损失，尤其可能违反预算、品类或规格等硬约束，所以是 -1.0。

合理停止或过早停止虽然任务没完成，但风险通常小于买错，因此负分较轻。

### Q28：步数惩罚为什么从第 16 步才开始？

前 15 步给模型合理的搜索、比较和规格核验空间，不鼓励为了省步数盲目购买。

第 16 步以后按区间递增扣分，重点压制长期无进展。它只改变 Final Reward，不改变终局类型。

### Q29：为什么不用 LLM 做在线 Reward？

在线 GRPO 需要 Reward 稳定、低延迟、可复现，而且不能在不同 Rollout 间漂移。LLM Judge 成本高、非确定、还可能读到不该读的信息。

因此主 Reward 使用确定性环境和约束核验；LLM Judge 只做离线轨迹诊断，不覆盖环境结果。

### Q30：如何防 Reward Hacking？

第一，模型消息里不暴露 Gold、Reward 和隐藏 TaskFacts。第二，价格按最终完整 variant 核验，不能拿搜索页最低展示价作弊。第三，规格和属性要有结构化字段或公开证据，不能只靠标题子串。

最后，Reward 输出逐约束证据，异常可以离线审计，而不是只有一个不可解释标量。

### Q31：reward_valid=false 为什么不能直接当 0 分？

因为它表示证据链或基础设施无法可靠判断，不代表模型做得一般。

如果当 0 分训练，会把环境问题错误归因给策略。GRPO 中只要一条轨迹 Reward 不可验证，我会把整个 prompt 组从更新中删除。

### Q32：Reward 还有什么局限？

它仍然主要是终局序列级 Reward。模型前 20 步做得很好，最后选错规格，整条轨迹共享同一个负 Advantage，信用分配比较粗。

后续可以尝试更可靠的过程奖励、关键状态 Value 或分阶段 Reward，但前提是不能引入新的不可审计信号。

## 四、GRPO 与在线训练

### Q33：请简单解释 GRPO。

同一个 Prompt 采多条回答或轨迹，用组内平均 Reward 作为相对基线。高于组均值的轨迹得到正 Advantage，低于均值的得到负 Advantage。

在这个项目里，一组是同一购物任务的 4 条真实环境轨迹，不是一段文本的 4 个答案。

### Q34：本项目的 Advantage 怎么算？

可以近似写成 A_i = R_i - mean(R_group)。当前配置不再除以组内标准差。

终局 Reward 是轨迹级的，但 Advantage 会作用到该轨迹参与训练的 Assistant Response Token 上。

### Q35：为什么借鉴 Dr.GRPO 去掉标准差归一化？

Reward v4 是离散终局分数加小幅步数惩罚。如果组内只差一点点步数惩罚，标准差会非常小，再做除法可能把噪声放大。

所以先过滤 Reward Range 不超过 0.025 的低差异组，再只做均值中心化，让 Advantage 保留原始 Reward 的相对尺度。

### Q36：GAPO 风格动态重采样怎么做？

每个 Prompt 先采 4 条。要求组内至少有一条 Gold 或 Valid，Reward 有效，而且 terminal utility 的 max-min 大于 0.025。

不合格组最多重采一次；第二次仍没信号就丢弃。这样把在线算力集中到有正负对照的学习前沿，而不是全成功、全失败或近似同分组。

### Q37：为什么一组是 4 条？

2 条的相对估计噪声比较大，也更容易同分；更多条会提高采到成功轨迹和稳定排序的概率，但成本线性上升。

n=4 是当前单卡 GPU、8 个 Agent worker 和 max_num_seqs=8 下的工程折中，不是理论最优常数。

### Q38：0/4 和 4/4 为什么都不适合更新？

0/4 往往只有不同形式的失败，缺少正确行为锚点。4/4 如果 Reward 和效率也接近，组内 Advantage 接近 0。

GRPO 需要相对差异，不是 Rollout 数量越多越好。

### Q39：为什么采用无 KL GRPO？

我想先观察任务 Reward 对 SFT Policy 的直接优化效果，所以关闭了 KL Reward 和 Actor KL Loss。

稳定性主要靠 LoRA、小学习率 1e-6、PPO Clip 0.2、低差异组过滤和独立 Final-240 验收。训练日志里的 KL 可以作为诊断，但没有进 Loss。

### Q40：完全不用 KL 不危险吗？

有风险，所以不是说 KL 永远没用。当前策略更新规模较小，起点又是已经能完成任务的 SFT 模型，因此先用其他约束控制漂移。

如果后续扩大训练步数、提高学习率或者出现通用能力退化，我会重新评估 KL 或更严格的参考策略约束。

### Q41：PPO Clip 在 GRPO 中有什么作用？

GRPO 负责相对 Advantage，PPO Clip 负责限制新旧策略概率比，避免单次更新过大。

两者不是替代关系。当前上下 Clip 都是 0.2。

### Q42：为什么使用 seq-mean-token-mean？

长失败循环会产生更多 Token。如果直接全 Token 平均，长轨迹会因为 Token 多而隐式拥有更大权重。

先在每条轨迹的有效 Token 内求均值，再在轨迹之间求均值，可以让每条轨迹权重更接近相等。

### Q43：在线 Probe 是什么？

Probe 是用当前策略真实跑候选任务，观察每题 4 条轨迹的成功数、Reward 差异和有效性，再决定是否进入训练池。

它比用静态难度标签更直接，因为任务难不难取决于当前 Policy，而不是题目看起来多复杂。

### Q44：为什么要剔除零成功、全成功和 Reward 异常 Probe？

零成功组缺正确锚点，全成功组通常差异太小，Reward 异常组不可信。把它们都塞进训练只会浪费 Rollout 和 GPU。

动态采样的目标不是让数据越多越好，而是提高每次更新中有效相对信号的比例。

### Q45：GRPO100 比纠错 SFT 提升了多少？

正确购买从 164/240 提升到 173/240，净增 9 题；平均 Final Reward 从 0.3368 提升到 0.4238。

严格 Gold 从 142 提升到 153，增 11 题。面试时要说明你说的是哪一个成功指标。

### Q46：veRL 和 vLLM 分别负责什么？

veRL 负责训练调度、Rollout Batch、Log Prob、Advantage 和 PPO 更新；vLLM 负责高吞吐异步生成。

项目自己的 AgentLoop 把模型生成、工具调用、环境 Step、Observation 投影、上下文管理和 Reward 结算接进 veRL。

### Q47：LoRA Actor 更新后，vLLM 怎么拿到新权重？

训练侧 Actor 持有可更新 LoRA 参数，Rollout 侧需要在更新边界同步或合并最新 Adapter，保证下一批轨迹来自当前策略。

这是在线 RL 与离线 SFT 的重要区别：Rollout Policy 和训练 Policy 不能长期失配，否则 old logprob、行为策略和更新目标会失真。

### Q48：为什么 GRPO 的数据里不放 Teacher 答案？

GRPO 是在线 on-policy 优化，训练输入只需要任务 Prompt 和环境身份。轨迹由当前 Policy 在环境里现跑出来。

如果把 Teacher 答案塞进去，就变成离线模仿或者混合训练，不再是纯粹的在线策略优化。

## 五、Harness 与长上下文工程

### Q49：Harness 到底是什么？

Harness 是模型和有状态 ShopSimulator 之间的执行控制层，不是规则选品器，也不是环境本身。

它负责协议、状态、预算和生命周期：约束单步 Tool Call、校验最新页面动作、投影 Observation、管理上下文、创建和释放 Session，并区分模型失败与基础设施失败。

### Q50：当前 8 个购物工具有哪些？

核心 8 个是 search_products、open_product、select_option、back_to_search、prev_page、next_page、buy_now 和 finish_without_purchase。

旧版四个信息子页工具被移除，非空 Description、Features、Reviews 和 Attributes 合并进商品详情，减少不必要跳转和状态漂移。

### Q51：为什么工具不是越多越好？

每个工具都会占 Schema Token，也扩大模型的动作空间。低频工具如果只是把同一信息拆成更多页面，反而会增加往返和出错概率。

工具设计要服务于清晰的状态转移，不是把环境所有内部能力原样暴露给模型。

### Q52：动态 Tool Schema 是什么？

不是每轮都把全部工具给模型，而是根据最新页面和当前阶段，只暴露真正合法的动作。

例如候选选择阶段只开放 open_product，规格阶段只开放 select_option，终局阶段只开放 buy_now 和 finish_without_purchase。这样模型可见工具、Guard 允许动作和环境可执行动作更一致。

### Q53：Schema 校验、动态工具暴露和 Action Guard 有什么区别？

Schema 校验管格式，比如参数类型、必填字段和额外参数。动态工具暴露缩小模型当前能选的动作集合。

Action Guard 再结合最新 Observation 检查语义合法性，比如 ASIN 是否在当前搜索页、Option 是否属于当前商品、按钮是否真的存在。

### Q54：为什么环境已经会拒绝非法动作，还需要 Guard？

环境拒绝是最终防线，Guard 是模型侧的早期反馈和状态对齐层。

Guard 可以给出更明确的错误原因、避免无意义环境调用、统一训练和评测记录，并保证模型可见目标与允许目标一致。

### Q55：为什么每轮只执行一个 Tool Call？

第二个调用生成时依赖的还是旧 Observation。第一个动作执行后页面可能已经变化，继续并行执行会产生过期动作和竞态。

所以多调用时只保留第一个并记录其余调用，下一轮基于新 Observation 再决策。

### Q56：Observation v2 为什么不直接把原始页面全部塞给模型？

原始环境状态可能很长，还可能含隐藏字段和对决策没帮助的内容。直接塞进去既浪费上下文，也可能泄漏 Gold 或 Reward。

Observation v2 只保留公开页面、商品边界、价格、规格、按钮和必要导航状态，再按页面类型分配 Token 预算。

### Q57：Observation 投影为什么不能简单截字符串？

简单截断可能删掉某个 ASIN、规格按钮或者 footer，导致模型看到的动作目标与 Guard 允许集合不一致。

投影后会再次检查搜索页 ASIN 集合和非搜索页按钮集合。无法安全放入预算时，轨迹标成基础设施无效，而不是悄悄改变任务。

### Q58：C1–C4 候选记忆是什么？

每条轨迹保存最先核验的 4 个公开候选，包括 ASIN、价格、标题、品牌、品类、规格和重新定位线索，编号在轨迹内稳定。

它只是工作记忆，不代表推荐排序，也不会让历史 ASIN 自动变成可点击对象。模型仍要重新搜索，等 ASIN 再出现在最新页面后才能打开。

### Q59：候选收敛机制怎么工作？

当候选数达到阈值或连续 6 步无实质进展时，不直接判 Loop，而是收紧 Tool Schema，强制模型基于已核验候选完成选择、规格闭合和终局动作。

GRPO230 v3 中有 34 题进入这个阶段，16 题转化为正确购买，其中 12 个 Gold、4 个 Valid。

### Q60：候选强制阶段会不会替模型选答案？

不会。Harness 只限制动作空间和保留公开候选证据，最终选哪个商品、选什么规格、买还是放弃仍由模型决定。

如果 Harness 根据 Gold 排序候选，那才是泄漏和规则代做。

### Q61：为什么按完整 Assistant–Tool 组裁剪历史？

如果只删 Assistant Tool Call 或只删 Tool Result，历史消息结构会变得不合法，模型也无法理解某个 Observation 从哪里来。

按完整交互组裁剪可以保持消息、Token Mask 和 Log Prob 对齐。最近页面、候选记忆和关键终局状态必须优先保留。

### Q62：训练和评测 Harness 为什么不是同一个循环？

评测使用显式 while-loop 和普通 OpenAI-compatible Client；GRPO 使用 veRL ToolAgentLoop 和异步 vLLM。

两者共享工具定义、Guard、Observation 和上下文算法，但生命周期封装不同，所以任何合同改动都必须同时测试两条路径。

### Q63：如何避免并发 Rollout 串状态？

每条 trajectory 创建独立 ShopSimulator Session，用 ContextVar 绑定当前环境和运行状态，所有退出路径都在 finally 中释放租约。

Harness 的 latest_observation 只是模型可见快照，环境真实状态仍由 Session 权威持有。

### Q64：为什么同步环境调用要放到线程里？

GRPO Rollout 是异步的，如果直接在事件循环里执行同步 reset 或 step，会阻塞其他并发轨迹。

通过线程封装同步调用，可以保留现有环境接口，同时不拖死异步生成和其他 Agent worker。

## 六、评测与归因

### Q65：Final-240 是怎么构成的？

Core-180 是 9 个一级领域，每个 20 题；Challenge-60 是 6 个困难切片，每个 10 题。

困难切片包括搜索改写、候选比较、价格语义、多规格、证据核验和长链路。

### Q66：为什么不能只看环境 Reward？

环境 Reward 能回答最终买得对不对，但不能完整解释搜索是否合理、候选有没有比较、证据是否充分、为什么循环，以及工程成本是否可接受。

所以评测拆成终局结果、约束满足、轨迹质量和确定性效率四个面板。

### Q67：冻结 Rubric 是什么？

每道题把用户要求拆成可审计条目，总计 1,769 条，状态是 satisfied、violated、unknown 或 not_applicable。

Rubric 在看模型结果前冻结，避免根据某个模型的表现临时改标准。

### Q68：LLM-as-Judge 如何避免泄漏？

Judge 只看 Query、冻结 Rubric、Actor 可见轨迹和白名单行为指标，不看 Gold、Reward、Reward Detail 或其他模型结果。

Judge 只做五维过程诊断，不覆盖环境成功判定，也不生成一个不可解释的综合总分。

### Q69：五个轨迹维度是什么？

搜索策略、候选利用、证据核验、决策质量和终止效率，每项 0、1、2 分并要求给出轨迹证据。

GRPO230 v3 相比 Qwen3.8-27B v3，五维平均约高 0.02 分，同时 Rubric satisfied 多 56 条。

### Q70：pass@4 和 pass⁴ 分别表示什么？

pass@4 表示同一任务独立运行 4 次，只要至少成功一次就算通过；pass⁴ 表示 4 次必须全部成功。

GRPO230 的四轮结果是 pass@4 87.50%、pass⁴ 70.00%。前者衡量能力上限，后者更接近稳定性。

### Q71：为什么单次成功率高，pass⁴ 仍会低很多？

因为长程 Agent 的误差会沿多步累积，搜索词、候选和规格选择也有随机性。一次能成功不代表每次都稳定。

因此只报 pass@k 容易掩盖脆弱性，最好同时报告全成功率、单次成功率和失败类型。

### Q72：如何比较 GRPO230 v3 和 27B？

同一 Final-240 和 Harness v3 下，2B 的正确购买是 81.25%，27B 是 75.42%；严格 Gold 分别是 73.33% 和 67.92%。

但不能只下结论说小模型更强，还要说明 2B 接受了针对性 SFT 和 GRPO，比较的是“后训练系统”和“大模型基线”，不是纯参数规模实验。

### Q73：81.25% 的提升能全部归因于 GRPO 吗？

不能。GRPO230 v3 同时使用了更新后的 Harness v3，包括动态工具暴露、候选记忆和强制收敛。

所以准确说法是“GRPO Checkpoint＋Harness v3 的完整系统结果”。纯训练增益要看相同 Harness 下的配对实验。

### Q74：这个项目最大的局限是什么？

Reward 仍以终局为主，信用分配比较粗；环境是冻结商品快照，与真实电商的库存、噪声和页面变化还有差距；Harness 改进和模型改进有时难完全解耦。

另外 Final-240 的每个 Challenge 切片只有 10 题，适合诊断，不适合过度声称统计显著性。

### Q75：下一步你会怎么优化？

第一，做阶段级但仍可验证的过程 Reward，改善信用分配。第二，用严格同 Harness 的消融拆分 Candidate Memory、动态 Schema 和 GRPO 的贡献。

第三，提高多次运行稳定性，重点看 pass⁴、错误购买和预算违反，而不是只追单次成功率。

# 第二部分：XXXClaw 长程 Coding Agent

## 一、项目定位与 Agent Loop

### Q76：请用 30 秒介绍 XXXClaw。

XXXClaw 是基于 pi-mono 旧版 Mom 二次开发的长程 Coding Agent。它可以从 Slack 或飞书接收任务，通过 9 个工具操作真实代码仓库，并在 Docker 中运行命令。

我重点解决了模型提前停止、重启后状态丢失、工具越界和完成难验收四类问题，增加五状态 Goal 监督、会话恢复、分层 Memory、统一 Tool Runtime、安全审批和独立 Eval。最终 60 题、180 次固定重复评测达到 98.3% pass@3、81.7% pass³。

### Q77：哪些能力来自 pi-mono，哪些是你做的？

pi-mono 提供了模型抽象、基础 Agent Loop、SessionManager 和旧版 Slack Mom 外壳。

我做的是 Mom 层的工程增强：Goal 状态机和验收门禁、thread/channel/user 会话路由、global/channel Memory、上下文压缩策略、统一 Tool Runtime、WorkspaceGuard、Docker 和审批、飞书接入以及 Eval Harness。

不能把 pi-agent-core 的基础 Tool Loop 说成自己原创，准确表达是“复用底层循环，重构长任务可靠性闭环”。

### Q78：Coding Agent 的基础循环是什么？

宿主把消息和 Tool Schema 发给模型；模型生成 Tool Call；宿主校验并执行；Tool Result 追加回上下文；模型继续决策，直到合法终局。

模型本身不会真的执行函数，它只是生成结构化调用，执行权始终在宿主程序。

### Q79：Workflow、Chatbot 和 Agent 有什么区别？

Workflow 的路径主要由人预先写死；Chatbot 增加多轮对话；Agent 再增加工具和模型控制的动态路由。

风险高、路径可枚举的任务更适合 Workflow；需要现场探索代码和错误原因的任务更适合 Agent。

### Q80：为什么不直接使用 LangChain？

不是框架不好，而是 Coding Agent 的核心状态、工具和安全边界需要高度可见、可控、可调试。

pi-mono 已经提供了足够合适的底层抽象，我更愿意在清晰的 Tool Loop 上增加 Goal、审批和持久化，而不是再叠一层不必要的编排框架。

## 二、Goal 监督与客观验收

### Q81：为什么需要 Goal Supervisor？

普通 Agent Loop 把模型自然停止当成任务结束，但模型可能只是提前总结，代码和测试都没完成。

Goal Supervisor 把“模型这次不再调用工具”和“任务真的完成”分开。只要 Goal 仍是 active 或 verifying，外层就可以继续触发下一次 Attempt。

### Q82：五个 Goal 状态是什么？

active 表示继续执行；verifying 表示进入验收；complete 表示完成；waiting_for_user 表示缺少用户输入或审批；failed 表示失败或预算终止。

状态持久化在每个 Conversation 的 goal.json 中，进程重启后仍然可以恢复。

### Q83：这和简单写一个 while true 有什么区别？

while true 只会不断调用模型，没有生命周期语义，也不知道什么时候应该等待用户、验收、失败或恢复。

Goal 循环由持久化状态机驱动，每次继续前检查预算，完成前检查真实验证和证据，重启后从磁盘状态恢复。

### Q84：如何防止模型自称“测试通过”？

完成前必须真实执行验证命令。系统记录命令、退出码、输出摘要、时间和对应验收条件。

模型写一句“测试通过”不算证据；退出码非零、没有真实工具记录或证据覆盖不足，都不能进入 complete。

### Q85：为什么代码修改后旧验证会失效？

因为测试通过只证明当时那一版代码。验证后再 write、edit 或运行普通可能改变工作区的命令，旧证据就不再新鲜。

系统会自动清除验证有效状态，要求重新运行验收命令，避免“先测试、后改坏、仍然宣布完成”。

### Q86：验收条件如何设计？

创建 Goal 时把目标拆成可检查的 acceptance criteria。goal_complete 时，每条条件都要提交具体证据，而不是一个笼统总结。

开放式条件可以交给独立、无工具权限的 LLM Judge 复核；Judge 拒绝后回到 active 继续修复，Judge 故障采用 fail-closed。

### Q87：如何避免 Agent 无限续跑？

每个 Goal 有尝试次数、墙钟时间和主 Agent 成本预算，继续前统一检查，超限进入 failed。

准确说法是当前主要靠这些客观预算终止失控任务；不要夸大成已经有完善的语义级 no-progress 检测。

### Q88：用户暂停、等待和失败有什么区别？

waiting_for_user 表示需要用户输入或审批，任务不是失败，并且可以暂停墙钟预算。

failed 是终态，例如预算耗尽、显式取消或不可恢复错误。把两者分开可以避免 Agent 在缺权限时继续乱试。

## 三、会话恢复、上下文与 Memory

### Q89：会话如何隔离？

Slack 和飞书都支持 thread、channel、user 三种 Conversation scope，默认 thread 更适合 Coding Agent，一个线程对应一个任务。

scope 决定谁共享 context.jsonl，不等于长期记忆作用域。

### Q90：context.jsonl 保存什么？

它以 append-only 方式保存 user、assistant、Tool Call、Tool Result 和 compaction 节点，是 Conversation 的完整 Agent 轨迹。

进程重启后，SessionManager 重新打开同一文件，恢复最近分支，再补同步 log.jsonl 中未进入 Session 的用户消息。

### Q91：为什么使用 JSONL，而不是一个大 JSON？

JSONL 适合追加写和逐条恢复，进程崩溃时通常只影响最后一条未写完整记录，不需要重写整个文件。

它也方便审计、流式处理和定位某次 Tool Call。中间记录损坏必须报错，不能静默吞掉历史。

### Q92：上下文压缩什么时候触发？

优先依据 API 返回的真实 Token Usage，而不是用固定轮数猜测。接近窗口上限后，系统生成结构化 checkpoint，并保留按 Token 预算选择的近期原始消息。

checkpoint 包含目标、已完成工作、关键决策、下一步和文件操作，避免只做一段模糊聊天摘要。

### Q93：为什么压缩时也要保持 Assistant–Tool 组完整？

Tool Result 必须能找到对应的 Assistant Tool Call。切在中间会让消息结构非法，也会让模型看到没有来源的执行结果。

所以切点必须落在完整交互组边界，和购物 Agent 的长上下文原则一致。

### Q94：压缩后原始历史还在吗？

还在。系统向 context.jsonl 追加 compaction 节点，不会删除旧行。

模型下一次只看到 checkpoint＋近期消息，但磁盘上仍保留完整轨迹，便于审计和恢复。

### Q95：长期 Memory 怎么分层？

当前有 global 和 channel 两级 MEMORY.md。global 跨所有聊天位置共享，channel 只在当前 Slack 频道、DM 或飞书 chat 中共享。

每轮运行都会重新读取并加入 System Prompt。global 修改影响范围大，所以 remember 和 forget 需要审批。

### Q96：thread、channel、user 是三层 Memory 吗？

不是。它们是 Session 的划分策略，决定哪些消息共享一个 context.jsonl。

长期 Memory 目前只有 global 和 channel，没有 user MEMORY.md。

### Q97：为什么长期 Memory 不自动从所有对话抽取？

自动抽取很容易把临时信息、错误猜测或敏感数据变成长期事实。

当前采用显式 memory remember，更保守也更可审计。后续如果做自动抽取，需要增加置信度、冲突消解和用户确认。

### Q98：你用了向量数据库或 RAG 吗？

生产主路径没有。代码仓库里精确符号、路径和字符串非常重要，search、read 和命令行检索往往更直接。

当前长期 Memory 规模小，使用全量注入。Embedding、BM25 和语义冲突检测属于后续扩展，不能说已经实现。

## 四、Tool Runtime、Docker 与安全

### Q99：9 个 Agent 工具有哪些？

read、write、edit、search、bash、memory、goal、goal_complete 和 attach。

它们统一接入 Tool Runtime，但并不是 9 个工具全部在 Docker 中执行。

### Q100：Tool Runtime 统一做什么？

统一处理参数校验、超时、输出截断、错误格式化、危险操作分类、审批和 JSONL 审计。

这样每个工具不用重复实现一套安全逻辑，新增工具也必须经过同一入口。

### Q101：哪些工具在 Docker 里执行？

bash 在每次调用时创建受限 Docker 容器执行。read、write、edit、search 等文件工具运行在宿主 Node.js 进程中，通过 WorkspaceGuard 访问受限工作区。

两边操作的是同一个被挂载到 /workspace 的宿主目录，所以修改会真实落盘，不需要从容器复制回来。

### Q102：为什么不把所有工具都塞进 Docker？

文件工具需要稳定、精确地操作宿主工作区和做路径校验，放进临时容器并不会自动解决权限问题，反而增加复制、同步和错误处理复杂度。

当前分工是 WorkspaceGuard 限制路径，Approval 限制高风险意图，Docker 限制未知命令的系统影响范围。

### Q103：WorkspaceGuard 如何防目录逃逸？

它把工具路径解析到允许工作区，检查绝对路径边界；对已存在路径使用 realpath，再判断符号链接解析后的真实位置是否仍在工作区内。

同时拒绝 .env、凭据、运行数据等 protected path。只做字符串 startsWith 是不够的。

### Q104：Docker 做了哪些限制？

将明确授权的 Windows 项目映射到容器 /workspace，并限制资源、网络和运行时间。容器只负责命令执行隔离，不能替代 WorkspaceGuard 和审批。

安全设计要分层，因为任何单层都可能有漏洞。

### Q105：危险操作如何审批？

Tool Runtime 先做风险分类，命中高风险后暂停工具调用，把原因、命令预览和风险类型发送到 Slack 或飞书，由任务发起者 approve 或 deny。

审批结果也写入 tool-calls.jsonl，保证事后可追踪。

### Q106：如何处理工具输出过大？

在 Runtime 层统一设置字符或 Token 上限，保留头尾和截断标记，避免单次命令输出挤爆上下文。

完整原始结果如果确实需要，可以保存为审计文件或附件，而不是全部塞回模型。

### Q107：如何避免命令执行卡死？

每次调用有超时和资源限制，超时后终止对应执行，并返回结构化错误。

Goal 层还会继续统计 Attempt 时间和成本，避免工具频繁超时后无限重试。

## 五、多平台、多模型与 Eval

### Q108：Slack Socket Mode 的作用是什么？

它通过长连接接收 Slack 事件，不需要把公网 HTTP 回调直接暴露出来，适合本地或内网运行 Agent。

系统还要处理频道、线程、附件、消息更新和交互式审批，不能只实现收到一句话就调用模型。

### Q109：飞书接入如何复用 Slack 架构？

飞书长连接先把消息、群聊、线程、用户和附件事件规范化成统一内部事件，再复用 Conversation、Session、Goal、Memory 和 Tool Runtime。

平台层只负责身份和消息差异，Agent 核心不应该复制两套。

### Q110：如何支持多模型和兼容端点？

在 Provider 层统一模型请求、Tool Schema、Token Usage、耗时和成本字段，支持 DeepSeek、OpenAI API 和 OpenAI-compatible endpoint。

上层 Goal 和 Eval 只依赖统一的响应结构，不绑定某个厂商 SDK。

### Q111：为什么 Token Usage 要用 API 真实返回值？

不同模型的 tokenizer、缓存和服务端计费规则可能不同，本地字符估算会误差很大。

真实 Usage 同时用于上下文压缩触发、成本统计和不同模型的公平比较。

### Q112：60 题 Benchmark 怎么设计？

它覆盖歧义需求、异步边界、CLI 合同、配置迁移、原子更新、JSONL 恢复和凭证真实性等真实 Coding Agent 难点。

每题有隐藏 Grader，Agent 看不到测试源码，固定重复 3 次，总计 180 次，避免只看单次偶然成功。

### Q113：为什么需要隐藏 Grader？

如果 Agent 能直接看到所有验收测试，可能针对测试样例打补丁，而不是解决真实合同。

隐藏 Grader 在 Agent 结束后独立运行，也避免采信 Agent 自己提供的“测试通过”证据。

### Q114：pass@3 和 pass³ 怎么解释？

pass@3 是三次中至少成功一次，反映任务有没有能力做成；pass³ 是三次全部成功，反映稳定性。

98.3% pass@3 表示 59/60 至少成功一次；81.7% pass³ 表示 49/60 三次都成功。两者差距说明长程 Agent 仍存在随机性和偶发退化。

### Q115：为什么还要报告单次成功率和 p95？

pass@k 会受重复次数影响，不能代替单次可靠性。单次成功率 91.1% 更接近一次部署调用的预期。

p95 45.4 秒反映尾延迟，能发现少数任务因为搜索、工具失败或重复修复而拖慢。

### Q116：Eval 如何防止 Agent 修改测试？

评测工作区和 Grader 分离，运行前后检查测试文件完整性和关键哈希。Agent 只能操作明确授权的任务工作区，隐藏 Grader 在独立路径执行。

如果测试文件被修改或者证据来源不可信，该 Attempt 应判失败。

### Q117：XXXClaw 当前最大的局限是什么？

Goal 的无进展判断目前主要依赖次数、时间和成本预算，还没有成熟的语义级 progress detector；长期 Memory 没有语义召回和冲突消解；多个 Conversation 共享同一工作区时仍可能产生并发冲突。

此外，主 Agent 成本预算还没有完整覆盖所有 Judge 和基础设施成本。

### Q118：下一步怎么优化 XXXClaw？

我会优先做逐条 Criterion Verifier、工作区 Revision 指纹和原子任务锁，进一步提高验收真实性和并发安全。

Memory 侧再增加可审计的检索与冲突处理，而不是先盲目接一个向量库。

# 第三部分：大模型与 Agent 高频基础题

### Q119：SFT、DPO、PPO、GRPO 分别适合什么？

SFT 用示范数据教模型基本行为；DPO 用偏好对离线拉开 chosen 和 rejected；PPO 用在线 Reward 和 Value/Critic 做策略更新；GRPO 用同 Prompt 多样本的组内相对 Reward 估计 Advantage，通常不需要单独训练 Critic。

购物项目先 SFT 冷启动，再用 GRPO 做真实环境策略优化。

### Q120：什么是 on-policy？

训练数据主要由当前或非常接近当前的策略生成，策略更新后需要重新采样。

它的优点是优化目标和当前行为更一致，缺点是数据贵、不能无限复用旧 Rollout。

### Q121：LoRA 的原理是什么？

冻结原权重 W，只学习一个低秩增量 BA，用 W＋BA 近似全参数更新。

低秩矩阵参数少、显存低、易切换 Adapter，适合 SFT 和在线 RL 快速迭代。

### Q122：LoRA 的 r 和 alpha 是什么？

r 是低秩维度，决定适配容量和参数量；alpha 是缩放系数，常按 alpha/r 缩放增量。

r 越大不一定越好，会增加显存和过拟合风险，需要结合任务复杂度做验证。

### Q123：LoRA 和 QLoRA 的区别？

LoRA 通常冻结 BF16 或 FP16 Base，只训练低秩参数。QLoRA 进一步把 Base 权重量化到 4bit，再训练 LoRA，更省显存，但引入量化误差和额外算子复杂度。

购物项目有 94GB 级单卡并重视长上下文稳定性，所以使用 BF16 LoRA，关闭 QLoRA。

### Q124：为什么长上下文显存消耗大？

训练时不仅保存参数，还要保存每层激活、Attention 中间量和梯度；序列越长，激活和 Attention 成本快速增加。

Flash Attention 能降低中间显存和 IO，但不会让长序列变成零成本。

### Q125：Flash Attention 做了什么？

它通过分块计算和减少 HBM 读写，避免显式保存完整 Attention Matrix，在精确 Attention 结果下提升速度并降低显存。

核心收益来自 IO-aware，而不是改变 Attention 数学定义。

### Q126：RoPE 是什么？

RoPE 用与位置相关的旋转作用到 Query 和 Key，使注意力内积自然带上相对位置信息。

长上下文外推常围绕 RoPE 频率缩放，但外推长度增加不代表模型一定真正学会利用那么远的历史。

### Q127：KV Cache 是什么？

自回归生成时，历史 Token 的 Key 和 Value 不会变化，把它们缓存起来后，新 Token 只需要计算自己的 Q/K/V，不必重复前向整个前缀。

代价是 KV Cache 随层数、序列长度、并发数和 KV Head 数增长。

### Q128：MHA、MQA、GQA 有什么区别？

MHA 每个 Query Head 都有独立 K/V Head；MQA 所有 Query Head 共享一组 K/V，Cache 最省但可能损失能力；GQA 让一组 Query Head 共享一组 K/V，是质量和推理成本的折中。

### Q129：vLLM 为什么适合 Rollout？

它通过 PagedAttention、连续批处理和高效 KV Cache 管理提高并发生成吞吐，适合 GRPO 一次并行采多条轨迹。

但 Agent Rollout 还包含工具等待和多轮状态，所以高吞吐不只取决于模型生成，还取决于异步调度和环境延迟。

### Q130：ReAct 是什么？

ReAct 是 Reasoning 和 Acting 交替的 Agent 范式：模型根据当前 Observation 决定下一步行动，再根据工具结果继续推理。

生产系统不一定要把长推理文字暴露出来，但“观察—动作—新观察”的循环仍然是核心。

### Q131：Function Calling 是模型真的调用函数吗？

不是。模型只是生成符合 Schema 的结构化 Token，宿主解析、校验并执行对应函数，再把结果返回模型。

所以安全边界必须放在宿主，不能因为模型输出是 JSON 就默认可信。

### Q132：Tool、MCP 和 Skill 有什么区别？

Tool 是宿主直接提供的可执行函数；MCP 是发现和调用外部能力的标准协议；Skill 更像按需加载的任务说明和配套资源。

它们可以组合使用，但都不能替代宿主的权限控制和结果验证。

### Q133：Agent 为什么容易循环？

常见原因是 Observation 没有明确进展信号、搜索结果重复、历史过长导致早期目标被稀释、动作空间太宽，或者模型不知道什么时候应该收敛。

解决要同时从 Prompt、状态表示、工具空间、候选记忆、循环检测和 Reward 入手。

### Q134：如何区分模型失败和基础设施失败？

模型生成非法工具、错误购买或主动停止属于策略失败；环境超时、Observation 无法安全投影、Reward 证据缺失属于基础设施或样本有效性问题。

前者可以成为负样本，后者必须隔离，否则训练信号会被污染。

### Q135：什么是数据泄漏？

训练样本与评测题直接重叠只是最明显的一种。相同商品 family、近重复 Query、调参时反复看 Final 结果、Judge 看到 Gold 或其他模型结果，也都可能产生泄漏。

要冻结数据、哈希、Prompt、Harness 和评测协议，并保留运行 manifest。

### Q136：LLM-as-Judge 有哪些风险？

它会有随机性、位置偏差、模型偏好、提示敏感和信息泄漏风险。

因此要冻结 Prompt 和 Schema、做盲评、限制可见字段、要求证据、保留 Judge Invalid，并且不让它覆盖可程序验证的主指标。

### Q137：pass@k 的直觉公式是什么？

如果单次独立成功概率是 p，至少一次成功的概率近似是 1－(1－p)^k，全部成功概率是 p^k。

真实 Agent 多次运行不一定完全独立，所以最终还是应直接从重复实验统计，而不是只用公式推算。

### Q138：异步编程在 Agent 系统里解决什么问题？

模型请求、工具调用、网络和容器执行大量时间都在等待。异步可以让一个任务等待时继续处理其他任务，提高吞吐。

但 CPU 重任务或同步阻塞调用仍要放到线程或进程中，否则会卡住事件循环。

### Q139：FastAPI 在 Agent 项目里通常负责什么？

可以作为模型网关、工具服务、评测服务或任务控制 API，利用类型校验、异步请求和自动 OpenAPI 文档快速搭服务。

生产上还要补鉴权、限流、幂等、超时、日志和后台任务管理。

### Q140：Docker Bind Mount 和复制文件有什么区别？

Bind Mount 让容器直接看到宿主目录，容器修改会实时落盘；复制文件则是两个独立副本，需要额外同步。

Bind Mount 更适合 Coding Agent 操作真实仓库，但必须配合路径边界、只读挂载和敏感目录保护。

# 第四部分：行为面与压力追问

### Q141：两个项目中你最有成就感的优化是什么？

购物项目里是把 34 条原本会被判 Loop 的轨迹送入候选收敛，最终救回 16 条正确购买。它说明 Harness 不是简单加规则，而是在不泄漏答案的前提下改善决策条件。

XXXClaw 里是把“模型说完成”改成“系统拿真实退出码和证据验收”，让 Agent 的完成状态从主观文本变成可审计事实。

### Q142：讲一个失败的实验。

购物数据早期把过程门设得太严格，结果很多带 Guard 恢复的长轨迹被整条删掉，留下的数据集中在固定 8 步模板。

我复盘后发现“单条更干净”不等于“数据集更好”，于是区分可恢复和不可恢复缺陷，并增加数据集级长度、检索和动作模板约束。

### Q143：如果线上指标突然下降，你怎么排查？

先冻结变量，确认模型、Prompt、Harness、Reward、数据和推理参数是否真的是同一版本；再按任务配对看 failure→success 和 success→failure，而不是只看总平均。

然后拆终局类型、Guard、循环、上下文、工具错误和基础设施 Invalid，定位是策略退化、协议变化还是评测口径漂移。

### Q144：如果面试官质疑 81.25% 包含 Harness 增益怎么办？

我会直接承认，并说明这是完整系统结果，不把它包装成纯 GRPO 增益。

同时给出相同旧 Harness 下纠错 SFT 到 GRPO100 的提升：正确购买 68.33% 到 72.08%，平均 Reward 0.3368 到 0.4238；Harness v3 的贡献则用 34 条 Loop 中救回 16 条等数据单独解释。

### Q145：为什么你的项目可信？

因为我没有只给一个最好看的成功率，而是冻结数据和协议，区分严格 Gold 与 Valid，区分模型失败与基础设施失败，保留逐题轨迹、约束证据、运行哈希和多次重复结果。

XXXClaw 也不采信模型自述，而是用真实命令、退出码和隐藏 Grader 独立验收。

### Q146：你会怎么向非算法同学解释两个项目的共同点？

两个项目都在解决同一个问题：怎么把“模型偶尔能做对”变成“系统长期、稳定、可验证地做对”。

购物项目用环境状态、Reward 和 Harness 约束决策；Coding Agent 用 Goal、工具安全和独立测试约束执行。核心都是状态、边界和证据。

### Q147：如果只能保留一个亮点放简历，你选哪个？

投后训练岗位，我选“Teacher＋Reward＋在线 GRPO 的完整闭环”，因为能覆盖数据、算法和训练工程。

投 Agent 工程岗位，我选“Goal 证据验收＋安全 Tool Runtime”，因为它更接近真实生产 Agent 的可靠性问题。

### Q148：你认为自己还欠缺什么？

训练侧我希望补更系统的分布式训练和大规模多机实践；Agent 侧希望继续加强权限模型、并发事务和线上可观测性。

但我已经能从数据、模型、环境、工具、Reward 和 Eval 的完整链路定位问题，而不是只会调用某一个框架。

### Q149：为什么适合这个岗位？

我的优势是既做过真正的 on-policy 后训练，也做过真实仓库执行的 Agent Runtime，能把算法指标和工程可靠性放在同一套系统里考虑。

我不只关注模型能不能生成，还会追问状态是否一致、奖励是否可信、结果是否能复现、失败到底归因给谁。

### Q150：最后还有什么想补充？

我最想强调的是，这两个项目都不是 Demo 拼接。购物项目有冻结 Final-240、Reward 审计和多版本配对；XXXClaw 有持久化 Goal、真实验证、安全边界和隐藏 Grader。

如果有时间，我可以继续展开一条真实轨迹，从模型输入、Tool Call、状态变化一直讲到 Reward 或验收证据。

# 附录：面试中最容易说错的十句话

1. 不要说“68.33% 是严格成功率”；它是 Gold＋Valid，严格 Gold 是 59.17%。
2. 不要说“GRPO230 v3 的 81.25% 全是训练带来的”；它包含 Harness v3 增益。
3. 不要说“Reward Invalid 就是普通 0 分”；它是不可用于训练的无效样本。

5. 不要说“9 个 XXXClaw 工具都在 Docker 中”；只有 bash 进容器，文件工具受 WorkspaceGuard 控制。
6. 不要说“thread/channel/user 是三层长期记忆”；它们是 Conversation scope。
7. 不要说“Goal 已经有完善语义级无进展检测”；当前主要依靠 attempt、时间和成本预算。

10. 不要说“小模型普遍超过大模型”；只能说当前后训练系统在冻结购物协议下超过 27B 对照。
